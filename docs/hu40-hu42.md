# HU40–HU42 · Moderación, publicación y continuidad

Las HU40–HU42 cierran el alcance base de la V2. Las reseñas, recordatorios de medicación y pagos pertenecen a la V3 opcional.

| Historia | Entrega                                                                                   | Comprobación                                                                                                                                      |
| -------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| HU40     | Reportes con referencia, revisión privada y decisiones auditadas                          | Navegador, PostgreSQL local y contrato de desarrollo revertido                                                                                    |
| HU41     | Compilación identificable, publicación controlada y reversión de un artefacto compatible  | Actualización y regreso a la compilación anterior con service worker real en localhost. Pendiente la publicación HTTPS en el hosting del proyecto |
| HU42     | Alertas agregadas, límites de la aplicación y respaldo cifrado con ensayo de recuperación | Monitor activo en desarrollo y recuperación aislada de datos y archivos reales                                                                    |

## Reportar y revisar

1. Inicia sesión con correo confirmado. Abre una sede publicada y elige **Reportar información** o usa **Reportar** en un mensaje concreto del chat. Indica categoría y motivo de 10 a 1000 caracteres.
2. Conserva la referencia que devuelve el servidor. **Perfil → Mis reportes** permite consultar el estado y la decisión. Un reintento del mismo envío usa el mismo identificador.
3. En la cuenta administradora abre **Reportes y moderación**. **Abrir revisión autorizada** asigna el reporte y registra el acceso. En reportes de chat solo se muestra el mensaje elegido. El acceso al archivo, si existe, requiere una acción explícita y queda auditado.
4. Documenta el motivo y aplica la decisión. **Corregir ficha** actualiza datos públicos comprobados si coinciden las revisiones y no hay una edición pendiente. **Suspender** retira la ficha de nuevas consultas y reservas o restringe los nuevos envíos del chat. Las citas existentes requieren gestión separada. **Descartar** cierra el reporte conservando la decisión.
5. **Levantar suspensión** requiere motivo. Si se retiró una ficha, su responsable la debe reenviar a revisión para publicarla nuevamente.

El servidor valida pertenencia a la conversación, rol de administración, asignación y revisión. Administración no dispone de un explorador de chats privados. Al cerrar se elimina el snapshot de evidencia y se conserva la trazabilidad sujeta a eliminación de datos. La política se puede leer en **Privacidad**. Reportes y evidencia requieren conexión y se consultan por cuenta.

## Publicar una versión

`.github/workflows/release.yml` permite publicar en `staging` o `production` desde GitHub Actions. Producción toma el código de `main`. El pipeline compila después de las pruebas con variables públicas del ambiente, conserva el artefacto verificado durante 30 días y publica `/build.json` con commit, huellas de fuente y versión SQL esperada. El manifiesto del artefacto contiene la huella SHA-256 de cada archivo.

Configura dos ambientes si necesitas pruebas y producción por separado. Cada ambiente debe apuntar a su propio destino Pages y a su proyecto Supabase previsto. En GitHub Environments restringe production a la rama protegida `main` y guarda las credenciales de producción únicamente en ese ambiente. En un proyecto Pages administrado por este workflow, evita un segundo despliegue automático que omita los checks.

| Configuración del ambiente GitHub | Valores                                                                                                                          |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Variables de destino              | `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_PAGES_PROJECT`, `DEPLOY_PUBLIC_URL`, `SUPABASE_PROJECT_REF`                                 |
| Variables públicas de compilación | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_GOOGLE_MAPS_API_KEY`, `VITE_GOOGLE_MAPS_MAP_ID`, `VITE_WEB_PUSH_PUBLIC_KEY` |
| Secretos de publicación           | `CLOUDFLARE_API_TOKEN` y `SUPABASE_ACCESS_TOKEN`, con acceso a los destinos correspondientes                                     |

En Supabase configura las URL de Auth, los orígenes de las funciones y los secretos de backend a partir de `.env.example`. Ajusta las restricciones de Google Maps para el dominio publicado. Configura las tareas operativas del proyecto antes de la aceptación. Las credenciales del backend se guardan en Supabase o GitHub según su propósito. En local se mantiene un único `.env.local`.

La acción `deploy` verifica la integridad antes de aplicar migraciones pendientes y desplegar funciones. Antes de subir el frontend comprueba el esquema y las solicitudes OPTIONS y POST de las funciones desde el origen previsto. Después verifica las rutas profundas, los tipos de contenido y las huellas de los archivos que sirve el hosting. Pages usa su fallback SPA nativo. Una regla general de reescritura también alcanzaría los archivos estáticos. [Rutas SPA en Cloudflare Pages](https://developers.cloudflare.com/pages/configuration/serving-pages/#single-page-application-spa-rendering).

```powershell
npm run release:verify -- https://tu-proyecto.pages.dev/
npm run release:verify -- https://tu-proyecto.pages.dev/ --artifact release-manifest.json
```

Para volver a una versión anterior usa `rollback` y el ID de ejecución que generó el artefacto anterior aprobado. Debe coincidir el ambiente, el proyecto y la versión SQL probada. Esto repone el frontend. Si también cambió el contrato del backend, prepara una corrección compatible hacia adelante y verifica primero en pruebas. GitHub permite configurar revisores del ambiente según el plan y las reglas del repositorio.

Tras el despliegue o reversión, anota el commit y valida con cuentas de prueba el acceso, la búsqueda, una cita y el chat. Recarga una ruta directa y comprueba el comportamiento online y offline desde una instalación existente. La publicación y reversión en el dominio real aún requieren el proyecto Pages y su configuración.

En el ensayo con Wrangler Pages 4.160.1, dos builds del mismo esquema se sirvieron por HTTPS local. Se comprobó el recorrido A → B → A en Chromium con el service worker activo y confirmación del usuario. Cada etapa pasó 27 respuestas con huellas coincidentes. El certificado de desarrollo se confió únicamente en los procesos de la prueba.

## Supervisar y recuperar

**Administración → Estado y límites de operación** muestra alertas técnicas con umbral, valor observado y última comprobación. Revisar una alerta confirma que se atendió, y se cierra al recuperarse el indicador. El job `veterinary-operation-monitor` revisa cada minuto. Las alertas se consultan en la aplicación.

| Indicador                        | Configuración inicial                                                                                                                                    |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fallos de API, mapas y funciones | 5 por componente en 5 minutos                                                                                                                            |
| Notificación vencida en cola     | Al menos una con atraso superior a 10 minutos                                                                                                            |
| Entregas push fallidas           | 3 en una hora                                                                                                                                            |
| Incidencias de llamada           | 3 en 15 minutos                                                                                                                                          |
| Mapas y rutas                    | Aviso al 80 %. Máximo de 300 cargas y 100 cálculos al día, hora de Bogotá                                                                                |
| Archivos                         | Aviso al 80 % del presupuesto inicial de 100 MiB al sumar ambos buckets. Límite de reserva del chat por presupuesto y límites por archivo en cada bucket |

El límite de mapas contabiliza intentos que pasan por la PWA. Para controlar consumo y facturación configura también las restricciones de clave, cuotas y alertas de presupuesto del proveedor. Los códigos técnicos no incluyen ubicaciones ni contenido privado. Los fallos de la aplicación se depuran a los siete días y los intentos de mapa/ruta a los treinta días.

El operador usa los secretos de recuperación del `.env.local` raíz y el proyecto correspondiente. `npm run recovery:keys` crea el par solo si falta. Configura ese par en Supabase mediante `deploy:secrets` o el procedimiento Vault de `supabase/operations/configure_recovery.sql`. Mantén las claves separadas de las copias. El [respaldo de base de Supabase](https://supabase.com/docs/guides/platform/backups) debe complementarse con los objetos de Storage.

```powershell
npm run recovery:backup -- --out backups/copia-2026-11-19.json.enc
npm run recovery:rehearse -- --backup backups/copia-2026-11-19.json.enc
```

La función `operations` exige credencial de operador y cifra con AES-256-GCM. Incluye tablas de aplicación, referencias de identidad y archivos de ambos buckets con manifiesto, tamaño y SHA-256. Excluye sesiones, claves de servicios y suscripciones push activas. Los archivos de copia y el registro de eliminaciones están excluidos de Git. Programa una copia diaria para sostener el objetivo de recuperación y conserva una copia cifrada separada con acceso restringido. La copia integrada está acotada a 250 archivos, 32 MiB de bytes y 20 millones de caracteres de datos. Si se supera algún límite, el operador debe preparar y ensayar una copia PostgreSQL y Storage por lotes.

Ensayo real en desarrollo el 19 de noviembre de 2026: 34 tablas, 165 filas, 5 archivos con 1.800.137 bytes y 66 referencias de clave foránea verificadas. Se comprobó aislamiento por cuenta. La copia tenía unos 29 segundos de antigüedad y el ensayo duró 1,99 segundos. Los objetivos iniciales son una copia de hasta 24 horas (RPO) y recuperación en hasta 60 minutos (RTO). Son objetivos operativos para repetir el ensayo.

El ensayo exige las 34 tablas declaradas, incluidas las vacías, y un historial continuo de migraciones compatible. Coteja las eliminaciones del manifiesto interno con las de la base respaldada y con el registro acumulado suministrado al ensayo. Después restaura PostgreSQL embebido y los archivos temporales, reaplica las eliminaciones y comprueba las huellas. Las pruebas cubren una eliminación iniciada en la copia y otra iniciada después de tomarla.

Por defecto se consulta el registro de eliminaciones en Supabase. `--ledger archivo.enc` permite ensayar con un registro archivado. El informe guarda el origen y la fecha del registro, que es el límite de las eliminaciones comprobadas en el ensayo. Antes de abrir acceso al destino de una recuperación real, obtén y reaplica el registro vigente. Comprueba la sesión, archivos, citas y chat en el destino. Mantén suspendidas las entregas push y las salas antiguas durante la recuperación. Quedan pendientes el ensayo integral en otro Supabase con Auth y Storage gestionados y la programación externa de copias.

En desarrollo están aplicadas las migraciones 24 y 25. Las seis funciones Edge están activas. El contrato SQL `supabase/tests/hu40_hu42.sql` se ejecutó con rollback y permanecieron cinco cuentas, dos citas, cuatro mensajes y cinco archivos. La demostración completa todavía requiere la URL HTTPS, LiveKit entre dos equipos, recepción push e instalación física.

Pasaron 302 pruebas Vitest/PostgreSQL en 37 archivos y 130 recorridos Playwright con `CI=true`. También pasaron lint, tipos y Deno para las seis funciones. La compilación con el entorno real respondió en ocho rutas locales y coincidió con el esquema remoto. Se verificaron las huellas de 25 archivos y el rechazo de un archivo alterado, una ruta fuera del artefacto y un ambiente o esquema incompatible. La búsqueda de valores privados del entorno en el build devolvió cero coincidencias.
