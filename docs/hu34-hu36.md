## HU34: descarga y consulta local

En **Explorar → Directorio sin conexión**, pulsar **Guardar directorio sin conexión** o **Actualizar descarga offline**. Se descargan todas las páginas de publicaciones y servicios activos. Solo se incluyen servicios de sedes pertenecientes a una publicación aprobada, incluso cuando la cuenta conectada pudiera leer oferta privada de su establecimiento.

`offline-directory.ts` guarda un paquete completo identificado como `offline-directory:v1` y sus índices por establecimiento en una transacción de `public_snapshots`. Si falla una página, la red o una escritura por cuota, no se reemplaza la descarga anterior. Una respuesta parcial no se anuncia como descarga completa.

La copia incluye nombre, dirección, teléfono, horarios declarados y servicios. La búsqueda y los filtros usan esas publicaciones/servicios locales, también al abrir una ficha que no se había visitado individualmente. La fecha de la descarga se conserva: recuperar la copia no convierte sus datos en información recién consultada.

El directorio y la ficha muestran antigüedad y advierten que horarios o servicios pueden haber cambiado. La apertura actual se considera desconocida offline; los cupos requieren revalidación remota.

Mapas Google, rutas y archivos remotos no forman parte de esta descarga. Sin mapa aparece el listado con direcciones/teléfonos. Las imágenes ausentes o fallidas muestran el sustituto de marca. La descarga de fichas no implica descarga de sus imágenes ni de mensajes privados. El catálogo público se conserva al cerrar sesión; los datos privados se purgan por cuenta según la decisión del usuario.

La primera visita debe completarse online mediante build/preview o HTTPS para preparar el shell. Sin una descarga previa puede existir caché parcial de páginas visitadas; si no hay datos guardados, se informa esa ausencia y se mantiene la interfaz/listado accesible.

## HU35: qué se conserva

**Cuenta → Pendientes y sincronización** (`/cuenta/pendientes`) reúne el trabajo local. Inicio y Cuenta muestran un acceso de aviso cuando existen pendientes. Reabrir la app no convierte un borrador en una solicitud recibida o confirmada.

| Dato                  | Persistencia e identificador                                         | Autorización para enviar                                                 |
| --------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Favorito y nota       | `preferences` + `outbox`, operación/revisión en la misma transacción | Sincronización existente de preferencias y acción manual                 |
| Horario preparado     | `availability_drafts` + `outbox`, UUID estable                       | Se vuelve a consultar, elige mascota y solicita explícitamente           |
| Solicitud de cita     | `appointment_request_drafts` + `outbox`, `p_id` estable              | Botón del formulario o **Revalidar y enviar solicitud guardada**         |
| Cambio de cita        | `appointment_change_drafts` + `outbox`, `p_operation` estable        | Envío/reintento explícito del cambio                                     |
| Texto                 | `message_drafts` + `outbox`, UUID del mensaje estable                | **Enviar mensaje**, **Guardar mensaje pendiente** o reintento autorizado |
| Foto/voz              | `pending_attachments`, blob y metadatos/estado con UUID estable      | Envío o limpieza explícitos; conserva el protocolo de HU25–HU26          |
| Incidencia de llamada | `call_failures`, operación estable                                   | Registro autorizado y reintento explícito                                |

### Texto

El editor guarda el texto al cambiarlo. Solo se muestra **Borrador de texto guardado** después de confirmar la escritura local. Un borrador editable no se envía por abrir la app, recuperar red o sincronizar otros datos.

Al pulsar enviar se persisten primero el cuerpo y su intención de envío. Si no hay conexión, **Guardar mensaje pendiente** autoriza el reintento posterior pero conserva el mensaje local. Si la respuesta se pierde, el mismo cuerpo/UUID se recupera después de recargar y puede reenviarse sin duplicarlo.

Un intento incierto queda protegido frente a edición que lo sustituyera por otro mensaje. Se puede reintentar o descartar su copia local. Descartar no retira un mensaje que el servidor ya hubiera recibido. Se guardan hasta 50 borradores de texto por cuenta.

El historial recibido continúa en memoria, sin copia general de chat en IndexedDB. Se conserva únicamente un contexto mínimo de la conversación previamente autorizada para poder recuperar su editor offline. Enviar vuelve a comprobar el permiso actual del servidor.

### Citas

El formulario conserva mascota y horario durante el cambio de conexión. La lista de mascotas consultada queda disponible como referencia privada para preparar la solicitud offline.

Antes de una petición HTTP se guardan argumentos e identificador. La confirmación del servidor retira el borrador y completa su operación en una transacción local. Si falta respuesta se conserva el intento: el estado local no acredita reserva ni recepción remota. La solicitud recibida queda `requested` y aún necesita decisión del establecimiento.

La agenda de servidor continúa siendo la autoridad de ocupación, permisos, reglas, modalidad y mascota propia. Un horario guardado puede estar ocupado o vencido cuando se intente enviar. Se conserva la selección y el error para decidir. Las solicitudes inciertas no se sustituyen silenciosamente por otro horario; primero se reintentan o se descarta su copia local. Hay un límite de 30 borradores de solicitud por cuenta.

Descartar un borrador no cancela una cita remota ni retira una solicitud que pudiera haberse recibido. Para ello se usa el detalle y su operación de cancelación autorizada.

## HU36: reintento y conflictos

El centro funciona **en primer plano**, con sesión revalidada y la app abierta. El botón de sincronización procesa perfil/mascotas, favoritos/notas y textos cuyo envío ya se autorizó. Citas, cambios y archivos tienen botones separados para confirmar la acción concreta. Reconectar por sí solo no envía borradores de citas o texto.

`send_chat_message`, `request_appointment` y `change_appointment` reutilizan los IDs persistidos; el servidor devuelve el efecto previamente registrado cuando corresponde. La operación no se declara completada hasta recibir y validar la respuesta. Un fallo de sesión/red o permiso conserva los datos. Las acciones desconocidas también permanecen pendientes, con un aviso, sin marcarse como completadas.

Los reintentos se serializan por cuenta mediante Web Locks, junto con guardados y cierre de sesión. El fallback sin esa API coordina una pestaña; no se afirma bloqueo entre pestañas en ese navegador.

Una ocupación de cita o revisión incompatible muestra conflicto y conserva mascota, intervalo, motivo y operación. Se ofrecen revisión de la cita, consulta de otro horario y descarte de la copia local. Para un cambio cuyo acuse se perdió, el centro permite reintentar su operación original aunque el detalle ya muestre otra revisión.

Las notas conservan su resolución explícita. El centro muestra nota local y versión remota consultada, y permite **Conservar mis cambios** o **Usar datos del servidor**. No sobrescribe automáticamente la versión local en conflicto.

La observación reactiva del centro consulta solo Dexie. La comprobación de Auth y de huella criptográfica se hace en la lectura autorizada, fuera del observador, para conservar las notificaciones de cambios locales. Ver [reglas de liveQuery](https://dexie.org/docs/liveQuery%28%29).

### Sesión y almacenamiento

Los datos privados requieren la misma cuenta, sesión SDK vigente y comprobante local generado tras validar `getUser` (propietario, vencimiento y huella del token). No se guarda otra copia del token en IndexedDB. La sesión local no autoriza escrituras remotas; sincronizar exige validación actual del servidor.

Al expirar la sesión, la interfaz oculta los datos privados aunque la pestaña siga abierta. Al recuperar la red se comprueba el acceso. Los pendientes permanecen almacenados para la misma cuenta. El cierre sigue exigiendo decidir sobre los pendientes antes de purgar; el conteo evita duplicar una intención que aparece tanto en su tabla como en outbox.

IndexedDB no está cifrado y depende del almacenamiento del navegador. Borrar los datos del sitio, el perfil del navegador o perder el dispositivo puede eliminar pendientes no enviados. **Solicitar conservación del almacenamiento** usa la API de persistencia si el navegador la admite; la concesión depende de él y no garantiza una copia de respaldo.

La aplicación ofrece esta sincronización sin depender de Background Sync. No se entregan tokens ni colas privadas al service worker para enviar operaciones mientras la sesión está cerrada o expirada.

## Comprobación funcional

1. Ejecutar `npm run build` y `npm run preview`. Abrir con conexión y completar la descarga desde Explorar.
2. Desconectar, recargar, buscar por servicio y abrir una ficha descargada que no se hubiera visitado. Comprobar dirección, teléfono, servicios y fecha; el mapa debe ofrecer listado y las imágenes ausentes un sustituto.
3. Acceder como dueño con una sesión comprobada, elegir servicio/horario/mascota y cortar la conexión. Guardar el borrador de solicitud, recargar y abrir Cuenta → Pendientes. No debe aparecer como reservada o confirmada.
4. Con una conversación autorizada, escribir texto y esperar el aviso de guardado. Desconectar y reabrir: el editor debe conservarlo. Marcar el mensaje pendiente, reconectar y comprobar que sigue sin envío hasta una acción explícita.
5. Simular una respuesta perdida tras aceptar un mensaje o solicitud. Reabrir el centro y reintentar: el servidor debe conservar un solo efecto y el cliente reutilizar el mismo ID.
6. Ocupar el horario desde otra cuenta, o cambiar una nota desde otro dispositivo. Comprobar conflicto, información local conservada y las opciones de revisión/resolución.
7. Probar sin `SyncManager`: la sincronización en primer plano sigue disponible. Con sesión expirada debe solicitar reautenticación y conservar los registros.
8. Cambiar de cuenta y comprobar aislamiento. Salir con pendientes debe exigir una decisión; el descarte autorizado elimina solo los datos privados correspondientes y conserva el directorio público.
